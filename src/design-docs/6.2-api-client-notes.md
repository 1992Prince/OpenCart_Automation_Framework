# APIHelper Utility Class - Point Form

## Why Create APIHelper Class Instead of Using Request Fixture Directly?

- When you have lots of API tests, it's better to have an `APIClient` (or `APIHelper`) utility for making calls instead of depending on the fixture directly
- This ensures baseURLs are kept in proper config/properties files
- Same test can be executed in different environments easily
- Provides centralized logging of requests, headers, responses for tracking and debugging purposes
- Maintains consistency across all API calls in the framework
- Reduces code duplication across test files

## APIHelper Class Structure

- Create a class called `APIHelper` and export it
- Keep `request` and `baseUrl` as **class-level private instance variables**
- `request` value is passed when creating the object (from fixture)
- `baseUrl` comes from environment config file
- Initialize both in the constructor
- When creating instance of this class, user needs to pass these two parameters
- Create instance of this class via a **fixture** (`apiFixture`)

## Generic Helper Methods in APIHelper

- Create generic instance methods like `get()`, `post()`, `put()`, `patch()`, `delete()`
- In each method:
  - Construct full URL using `baseUrl` + `endpoint`
  - Log the request (with headers and body if applicable)
  - Make the actual request to server
  - Extract status and body from response
  - Log the response
  - Return response as an object containing `status` and `body`

## APIHelper - GET Method

```javascript
async get(endPoint: string, headers?: Record<string, string>) {
    const url = `${this.baseURL}${endPoint}`;

    // Log Request
    console.log(`[REQUEST] GET -> ${url}`, headers ? { headers } : '');

    const response = await this.request.get(url, {
        headers: headers,
    });

    const status = response.status();
    const body = await response.json();

    // Log Response
    console.log(`[RESPONSE] ${status} <- ${url}:`, body);

    return {
        status: status,
        body: body
    };
}
```

- `endPoint` is required (e.g., `/v1/users`)
- `headers` are optional - pass them if needed, otherwise don't pass
- Returns object with `status` and `body`

## APIHelper - POST Method

```javascript
async post(endPoint: string, data: object, headers?: Record<string, string>) {
    const url = `${this.baseURL}${endPoint}`;

    // Log Request
    console.log(`[REQUEST] POST -> ${url}`, { headers, body: data });

    let response = await this.request.post(url, {
        headers: headers,
        data: data
    });

    const status = response.status();
    const body = await response.json();

    // Log Response
    console.log(`[RESPONSE] ${status} <- ${url}:`, body);

    return {
        status: status,
        body: body
    };
}
```

- `endPoint` is required
- `data` is the request payload (required for POST)
- `headers` are optional
- Returns object with `status` and `body`

## Creating APIHelper Instance in Fixture

```javascript
let apiHelper = new APIHelper(request, process.env.API_BASE_URL!);
```

- Create instance by passing `request` fixture and `baseUrl` from environment variable
- The `!` (non-null assertion operator) tells TypeScript that `process.env.API_BASE_URL` will not be null/undefined
- Now this `apiHelper` fixture can be used in all test specs

## Using APIHelper in Test Specs

```javascript
import { test, expect } from '../../src/fixtures/apifixtures'

const APIKEY = process.env.X_API_Key;

let AUTH_HEADER: Record<string, string> = {
    'X-API-Key': APIKEY ?? '',
}

test.skip('Get Users Test', async ({ apiHelper }) => {
    let response = await apiHelper.get("/v1/users", AUTH_HEADER);

    expect(response.status).toBe(200);
    expect(response.body).toBeGreaterThan(0);
});
```

- Import `apiHelper` fixture (don't destructure `request` directly)
- Pass auth headers as `Record<string, string>` type
- Call `apiHelper.get()` or `apiHelper.post()` etc.
- Validate response status and body

## Why Use Fixture for APIHelper?

- Fixture provides **dependency injection** - APIHelper instance is created once and reused
- Cleaner code - don't need to manually instantiate APIHelper in each test
- Automatic initialization with correct baseUrl from environment
- Fixture scoping ensures proper instance lifecycle management
- All tests get the same configured APIHelper instance
- Easy to modify or mock the APIHelper in future

## What About the Non-Null Assertion Operator (!) ?

- `process.env.API_BASE_URL!` uses the `!` (non-null assertion operator)
- TypeScript by default considers `process.env.API_BASE_URL` as potentially `undefined`
- The `!` tells TypeScript compiler: "I'm sure this value exists, don't show me undefined error"
- If the env variable is not set at runtime, it will be `undefined` anyway, but TypeScript won't complain during compilation
- Better practice would be to validate that env variable exists before using it

## Execution Strategy - BaseURL and Endpoints

- Keep **baseUrl** in config file (changes per environment)
- Hardcode **endpoints** in APIHelper methods (remain same across environments)
- When environment changes, only baseUrl gets updated - endpoints stay the same
- All requests and responses are logged automatically by APIHelper for debugging

## Running Tests in Serial Mode

- If you want all tests in a `describe` block to run **serially** (one after another), use `test.describe.serial()`:

```javascript
test.describe.serial('e2e crud tests', () => {
    // GET Test
    // POST Test
    // Validate created resource
    // UPDATE created user test
    // DELETE the created user test
});
```

- Tests will run in order - not in parallel
- Useful when tests depend on each other sequentially

## Independent Tests are Better

- **Our approach**: Don't follow serial execution strategy
- Instead, keep each test **independent** and complete:
  - Create user → Validate created user → Update it → Delete it → Verify deletion
  - All in a single test or within same test scope
- This ensures:
  - Tests can run in **parallel** without issues
  - No dependency on other tests' execution order
  - If one test fails, others are not affected
  - Each test is self-contained and can run standalone

## Handling Response Body - Array vs Object

**If `response.body` is an Array `[]`:**
- You can directly use `response.body.length`
- Example: `expect(response.body).toBeGreaterThan(0)`
- Or `expect(response.body.length).toBeGreaterThan(0)`

**If `response.body` is an Object `{}`:**
- `response.body.length` will **NOT work** - plain objects don't have `.length` property
- Instead, access the nested array: `response.body.users.length`
- Or check keys using: `Object.keys(response.body).length`
- Or access specific nested property directly

**Example:**
```javascript
// If response.body is array
const response = await apiHelper.get("/v1/users"); // returns [user1, user2]
expect(response.body.length).toBeGreaterThan(0); // Works

// If response.body is object
const response = await apiHelper.get("/v1/users"); // returns { users: [user1, user2] }
expect(response.body.users.length).toBeGreaterThan(0); // Works
expect(response.body.length).toBeGreaterThan(0); // Fails - no .length on object
```

## CRUD Validation Scenarios

**Create + Fetch + Validate:**
- Create a user
- Fetch the created user
- Validate the returned data matches what was created

**Create + Update + Fetch + Validate:**
- Create a user
- Update user with new values
- Fetch the user again
- Validate updated values are reflected

**Create + Delete + Fetch + Verify 404:**
- Create a user

## E2E Scenarios

- E2E tests validate complete workflows across multiple operations:
  - **Example 1:** Create token → Create order for user → Process payment with various options → Validate each response
  - **Example 2:** Create user → Update profile → Add to group → Create resource for that group → Delete group → Verify cascading effects

## Positive and Negative Scenarios

- Test both **positive** scenarios (happy path - operations succeed)
- Test **negative** scenarios (error cases - operations fail with appropriate error codes):
  - Invalid inputs → 400 Bad Request
  - Unauthorized access → 401 Unauthorized
  - Forbidden → 403 Forbidden
  - Resource not found → 404 Not Found
  - Server error → 500 Internal Server Error
- Validate error messages and response codes are correct for negative cases

## Q1: Why is the return type of generic methods `Record<string, string>`?

**Answer:**

The return type is **NOT** `Record<string, string>`. That's a misconception.

The return type should be an **Object with two properties:**
- `status: number` (HTTP status code like 200, 201, 404, etc.)
- `body: any` (response body - could be object, array, string, etc.)

**What is `Record<string, string>`?**
- `Record<string, string>` means an object where **all keys are strings and all values are strings**
- Example: `{ "name": "John", "age": "30", "city": "Mumbai" }`
- This type definition is used for **headers**, NOT for return type

**Why `Record<string, string>` is Used for Headers:**
- HTTP headers are key-value pairs where both keys and values must be strings
- Example: `{ "Content-Type": "application/json", "X-API-Key": "abc123" }`
- HTTP specification requires header values to be strings

**Correct Return Type Definition:**

```typescript
interface APIResponse {
    status: number;
    body: any;
}

async get(endPoint: string, headers?: Record<string, string>): Promise<APIResponse> {
    // ...
    return {
        status: status,      // number type
        body: body           // any type
    };
}
```

## Q2: Can the same fixture instance be shared with all tests when fixture scope is `worker` instead of `test`?

**Answer:**

**Yes, absolutely correct!**

When you set fixture scope to `worker`, the same APIHelper instance is shared across **all tests running in that worker process**.

**Difference Between Fixture Scopes:**

**Scope = `test` (Default):**
- APIHelper instance is created **fresh for each test**
- Each test gets its own new instance of APIHelper
- **Pros:** Isolation - no state sharing between tests
- **Cons:** Instance created multiple times (overhead if many tests)

**Scope = `worker`:**
- APIHelper instance is created **once per worker process**
- Same instance is **reused across all tests running in that worker**
- **Pros:** Instance created once, reused across all tests (more efficient)
- **Cons:** Tests might share state if APIHelper maintains internal state

**Current Approach (Scope = `test`):**

```typescript
export const apiFixture = base.extend<{ apiHelper: APIHelper }>({
    apiHelper: async ({ request }, use) => {
        // This runs BEFORE each test
        const apiHelper = new APIHelper(request, process.env.API_BASE_URL!);
        await use(apiHelper);
        // This runs AFTER each test
    },
});
```

- A new APIHelper instance is created for every test

**Better Approach (Scope = `worker`):**

```typescript
export const apiFixture = base.extend<{ apiHelper: APIHelper }>({
    apiHelper: async ({ request }, use) => {
        // This runs ONCE when worker starts
        const apiHelper = new APIHelper(request, process.env.API_BASE_URL!);
        await use(apiHelper);
        // This runs ONCE when worker shuts down
    },
});
```

**Setting Fixture Scope Explicitly:**

```typescript
apiHelper: {
    async ({ request }, use) {
        const apiHelper = new APIHelper(request, process.env.API_BASE_URL!);
        await use(apiHelper);
    },
    scope: 'worker'  // Share same instance across all tests in worker
}
```

**When to Use Which Scope:**
- Use `test` scope: When each test needs a fresh/isolated instance (safer, prevents state pollution)
- Use `worker` scope: When creating instance is expensive, and no state conflict exists between tests (more efficient)

**In Your Case:**
- If APIHelper doesn't maintain state between tests (just makes HTTP calls), `worker` scope is fine
- Since APIHelper is stateless (just a utility for making API calls), `worker` scope would be more efficient

## Q3: Why are `headers` passed as `Record<string, string>` but `data` passed as `object`? Can both be `object`?

**Answer:**

**Current Implementation:**

```typescript
async post(endPoint: string, data: object, headers?: Record<string, string>) {
    // ...
}
```

- `headers` → `Record<string, string>` (object with string keys and string values)
- `data` → `object` (generic object)

**Why Different Types?**

**Headers Must be `Record<string, string>`:**
- HTTP headers specification requires both keys and values to be **strings**
- Headers are strictly defined by HTTP standard
- Examples:
  ```javascript
  {
      "Content-Type": "application/json",
      "X-API-Key": "token123",
      "Authorization": "Bearer xyz",
      "Accept": "application/json"
  }
  ```
- All keys are strings, all values are strings
- This is enforced by HTTP standard specification

**Data/Payload is Generic `object`:**
- Request body (data) can have **mixed data types:**
  - String values: `{ "name": "John" }`
  - Number values: `{ "age": 30 }`
  - Boolean values: `{ "isActive": true }`
  - Array values: `{ "skills": ["Java", "Playwright"] }`
  - Nested objects: `{ "address": { "city": "Delhi" } }`
  - Null values: `{ "middleName": null }`

**Example - Request Body with Mixed Types:**

```javascript
const userData = {
    name: "Amit",           // String
    age: 30,                // Number
    isActive: true,         // Boolean
    skills: ["Java", "Playwright"],  // Array
    address: {              // Nested Object
        city: "Delhi",
        country: "India"
    },
    phone: null             // Null
};

await apiHelper.post("/v1/users", userData, authHeaders);
```

**Can Both Be `object`?**

- **Yes, technically both can be `object`**, but it's **NOT type-safe**
- If you use `object` for both, TypeScript won't validate that header values are strings
- TypeScript allows this but provides **no type checking**

**Example (Not Recommended):**

```typescript
async post(
    endPoint: string, 
    data: object,           // Generic object
    headers?: object        // Generic object - Not type-safe for headers!
) {
    // ...
}
```

- This compiles but TypeScript can't prevent you from passing `{ "key": 123 }` as headers
- Header value `123` is a number, not a string - violates HTTP standard

**Better Approach - Use Proper Types:**

```typescript
async post(
    endPoint: string, 
    data: Record<string, any>,           // More specific than object
    headers?: Record<string, string>     // Enforces type safety
) {
    // ...
}
```

- `Record<string, any>` for data = Keys are strings, values can be any type
- `Record<string, string>` for headers = Both keys and values must be strings
