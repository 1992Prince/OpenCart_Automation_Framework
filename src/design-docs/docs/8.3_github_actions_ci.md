# GitHub Actions / CI Interview Questions & Answers

## Q1. How have you integrated your framework with CI / GitHub Actions?

- Our Playwright framework is **CI-platform independent**, so it can be integrated with Jenkins, GitHub Actions, Concourse, etc.
- Currently, we are using **GitHub Actions** as our CI platform.
- We keep our workflow YAML files under `.github/workflows/`.
- We have separate workflows for activities like **smoke, regression, sanity and test-data creation**.
- A workflow can be triggered manually, through code events, or on a schedule, depending on the `on` section.
- Typical CI flow:
  - Provision the CI machine.
  - Checkout/clone the repository.
  - Set up dependencies.
  - Execute tests.
  - Upload test reports/artifacts.
  - Perform post-test activities such as publishing reports or sending notifications.
- We use the official **Playwright Docker image**, which already contains Node, Playwright, browsers and browser dependencies.
- After execution, we upload the **Playwright HTML report and test-results** as artifacts.
- We also publish the HTML report to **GitHub Pages** and send the execution status through **email and Slack**.

---

## Q2. Can you explain one of your workflow YAML files and its components?

- Sure. One of our workflows is used to execute our **Playwright E2E regression tests**.
- At the root level, the workflow mainly has three sections:
  - `name`
  - `on`
  - `jobs`

### `name`

- Defines the workflow name.
- This is what we see under the **GitHub Actions** tab.

### `on`

- Defines **when or how the workflow should be triggered**.
- Examples:
  - `workflow_dispatch` → manual execution.
  - `schedule` → scheduled execution.
  - `push` → trigger when code is pushed.
  - `pull_request` → trigger for pull requests.
- In our current workflow, we use `workflow_dispatch` with an environment dropdown such as QA, stage and dev.

### `jobs`

- Defines the actual work that needs to be performed.
- We can have **multiple jobs** under `jobs`.
- In our workflow:
  - `test` → executes Playwright tests.
  - `publish` → publishes the report and sends email/Slack notifications.
  - `summary` → provides the final pipeline summary.

### Inside a job

- `runs-on` → defines the runner machine.
- `container` → defines the Docker image in which our tests run.
- `environment` → selects the GitHub Environment.
- `steps` → defines the individual activities performed by the job.

### Test job

- Checkout repository.
- Install dependencies using `npm ci`.
- Run Playwright regression tests.
- Upload Playwright report.
- Upload test results.

### Publish job

- Waits for the test job.
- Downloads the Playwright report.
- Publishes it to GitHub Pages.
- Creates the report URL.
- Prepares status.
- Creates the email dashboard.
- Sends email and Slack notifications.

### Why separate test and publish jobs?

- We separate **test execution from reporting/notification activities**.
- This makes the workflow easier to maintain.
- The `publish` job uses `needs: [test]`, so it runs after the test job.
- We use `if: always()` so reporting and notification activities can still run even if tests fail.

## Q3. What are Actions in GitHub Actions and what Actions have you used?

- **Actions are reusable building blocks** that perform a specific task inside a GitHub Actions workflow.
- Instead of writing everything ourselves, we can use existing actions.
- In our workflow, we use:
  - `actions/checkout@v6` → checks out the repository code.
  - `actions/upload-artifact@v4` → uploads Playwright reports and test results.
  - `actions/download-artifact@v4` → downloads the report in the publish job.
  - `peaceiris/actions-gh-pages@v4` → publishes the Playwright report to GitHub Pages.
  - `dawidd6/action-send-mail@v3` → sends the execution report through email.
  - `8398a7/action-slack@v3` → sends execution status to Slack.
- We can also use `actions/setup-node` when we want to explicitly configure the Node.js version, but our current workflow uses the Playwright container.

## Q4. What are GitHub Pages and what is the purpose of using them?

- GitHub Pages is a service provided by GitHub to **host static web content**.
- We use it to host our **Playwright HTML report**.
- After test execution, we upload the Playwright report as an artifact.
- In the `publish` job, we download that report.
- We publish the report directory to GitHub Pages.
- We generate the GitHub Pages **report URL**.
- The same URL is included in our **email and Slack notifications**.
- Anyone receiving the notification can directly click the link and view the execution report.
- This is more convenient than sending the complete HTML report or artifact files through email.

## Q5. Suppose there is a requirement to share test execution count — passed, failed and skipped. How will you do it?

- Playwright can be configured to generate a **JSON report** containing execution details.
- We store that JSON report in a specific folder.
- In CI, we upload that report as an artifact along with other test results.
- In the `publish` job, we download and **parse the JSON report**.
- From the parsed data, we get total, passed, failed and skipped counts.
- We can then dynamically create the **email/Slack content** with these statistics.
- The same approach can be added to our current publish flow.

### Interview closing line

> The idea is to generate structured test results, pass them between jobs as artifacts, parse them in the publish job, and use the data in our notifications.

- It depends on the `test` job using `needs: [test]`.
- We use `if: always()` so this job can continue even when the test job fails.
- First, we **download the Playwright HTML report** generated by the test job.
- Then we publish that report to **GitHub Pages**.
- We generate the GitHub Pages **report URL**.
- We prepare the execution status.
- We create an HTML dashboard containing details such as environment, branch, run ID and report link.
- We send this dashboard through **email**.
- We also send the execution status and report links to **Slack**.

### Short version

> Test job is responsible for execution, while publish job is responsible for reporting and notifications. It downloads the report, publishes it to GitHub Pages, generates the URL, and shares the result through email and Slack.

## Q7. How are you handling secrets in CI?

- We manage secrets using **GitHub Secrets** instead of hardcoding them in the YAML.
- We mainly have two categories:
  - **Environment-level secrets** → application-specific values such as username, password, client ID, API tokens, etc.
  - **Repository-level secrets** → common values such as email credentials and Slack webhook.
- Locally, we keep environment-specific values in `.env` files and don't commit those files to Git.
- In CI, the selected GitHub Environment is specified using:

```yaml
environment: ${{ inputs.environment }}
```

- Then application secrets are accessed using:

```yaml
APP_USERNAME: ${{ secrets.APP_USERNAME }}
APP_PASSWORD: ${{ secrets.APP_PASSWORD }}
```

- This allows the same workflow to run against different environments while using the corresponding secrets.
- For repository-level/common secrets, we directly reference them where required:

```yaml
env:
  SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }}
```

## Q8. Suppose I need to run the same smoke job at different times in different environments using cron. Is it possible?

- **Yes, it is possible.**
- We can use GitHub Actions **scheduled workflows using cron**.
- For example:
  - 10 AM → STG
  - 4 PM → UAT
- Cron itself does **not provide the environment value** like our manual dropdown does.
- We need workflow logic to determine which environment should be used for each scheduled execution.
- We can use separate jobs/conditions or derive the environment based on the scheduled trigger.

### Short answer

> Yes, multiple cron schedules are possible in the same workflow. Since cron doesn't provide the environment input, we need workflow logic to map each schedule to the required environment.

## Q9. When the job runs through cron, how is the environment selected?

- With `workflow_dispatch`, the user manually selects the environment from the dropdown.
- With `cron`, there is **no manual environment selection**.
- So we need to determine the environment inside the workflow.
- For example:
  - 10 AM schedule → STG
  - 4 PM schedule → UAT
- We can use conditions based on the scheduled trigger, or use separate scheduled jobs for each environment.
- Then we pass the selected environment to the test execution through an environment variable.

### Example 1 — separate scheduled jobs

```yaml
jobs:

  smoke-stg:
    if: github.event_name == 'schedule'
    runs-on: ubuntu-latest
    env:
      ENV: STG
    steps:
      - name: Run Smoke Tests
        run: npm run test:smoke

  smoke-uat:
    if: github.event_name == 'schedule'
    runs-on: ubuntu-latest
    env:
      ENV: UAT
    steps:
      - name: Run Smoke Tests
        run: npm run test:smoke
```

### Example 2 — map schedule to environment

```yaml
on:
  schedule:
    - cron: '30 4 * * 1-5'    # 10:00 AM IST
    - cron: '30 10 * * 1-5'   # 4:00 PM IST

jobs:
  smoke:
    runs-on: ubuntu-latest

    steps:
      - name: Set Environment
        run: |
          if [ "${{ github.event.schedule }}" = "30 4 * * 1-5" ]; then
            echo "ENV=STG" >> $GITHUB_ENV
          else
            echo "ENV=UAT" >> $GITHUB_ENV
          fi

      - name: Run Smoke Tests
        run: npm run test:smoke
        env:
          ENV: ${{ env.ENV }}
```

### Interview answer

> Cron does not automatically select STG or UAT. Our workflow logic determines the environment based on the scheduled trigger and passes that value to the test execution.

## Q12. Why `npm ci` instead of `npm install`?

- `npm ci` is mainly intended for **CI environments**.
- It installs dependencies based on `package-lock.json`.
- It provides a more **consistent and predictable dependency installation**.
- It is generally faster and cleaner for automated CI execution.
- We use it in our workflow before running the tests.

### Short answer

> `npm ci` is preferred in CI because it installs the exact dependency versions defined in the lock file, giving us a consistent and repeatable build.

## Q14. What is the purpose of `if: always()`?

- Normally, if a previous job or step fails, dependent execution may be skipped.
- `if: always()` tells GitHub Actions to **run that job or step regardless of the previous result**.
- In our workflow, we use it for reporting and notification activities.
- Even if Playwright tests fail, we still want to:
  - Upload the report.
  - Publish the report.
  - Send email.
  - Send Slack notification.
- This is why the `publish` job has `if: always()`.

### Short answer

> `if: always()` is important for us because even when the test execution fails, we don't want to lose the test report or notification. We still want the reporting and notification activities to run.

## Q15. What is `needs: [test]`?

- `needs` is used to define a **dependency between jobs**.
- `needs: [test]` means the current job depends on the `test` job.
- So the `publish` job waits for the `test` job to complete.
- It also allows us to access the result of the test job using:

```yaml
needs.test.result
```

- We use that result to determine whether the tests passed or failed and prepare the email/Slack status.

### Short answer

> `needs: [test]` creates a dependency between the jobs. Our publish job waits for the test job, and then uses its result to prepare the reporting and notification status.

## Q16. How have you done the Slack integration with your CI?

- We integrated Slack using a **Slack Incoming Webhook**.
- First, we created a Slack app and selected our workspace.
- Under **Incoming Webhooks**, we enabled the webhook.
- We added the webhook to the required Slack channel.
- Slack then provided a **Webhook URL**.
- We stored that URL as a **GitHub Repository Secret** called `SLACK_WEBHOOK_URL`.
- In our GitHub Actions workflow, we use:

```yaml
uses: 8398a7/action-slack@v3
```

- We pass the webhook through:

```yaml
env:
  SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }}
```

- The workflow sends execution status, environment, branch and Playwright report links to Slack.

### Short version

> We use Slack Incoming Webhooks. We created a Slack app, enabled Incoming Webhooks, added it to our channel and stored the webhook URL as a GitHub secret. In our workflow, we use the Slack action and pass the secret to send the test execution status and report link.

- Each job can contain **multiple steps**.
- In our YAML:
  - `test` is one job.

### Short answer

> A job is a logical unit of work, and steps are individual activities performed inside that job.

## Q20. Why do you use `timeout-minutes`?

- We don't want a CI job to run **indefinitely**.
- `timeout-minutes` puts a maximum execution limit on the job.
- If the job exceeds that limit, GitHub Actions stops the job.
- This protects CI resources from getting stuck because of issues like application hangs, infrastructure problems or a test getting stuck.

### Short answer

> We use `timeout-minutes` as a safety limit so that a CI job doesn't run indefinitely and consume CI resources.

## Q21. Explain the cron expression.

Example:

```yaml
schedule:
  - cron: '0 10 * * 1-5'
```

- Cron is used to define a **schedule for workflow execution**.
- The five fields represent:
  - `0` → minute
  - `10` → hour
  - `*` → every day of month
  - `*` → every month
  - `1-5` → Monday to Friday
- So this means:
  **Run at 10:00 AM, Monday to Friday.**

### Important point

- GitHub Actions cron uses **UTC by default**.
- If the business requirement is in IST, we need to convert the required IST time to UTC.
