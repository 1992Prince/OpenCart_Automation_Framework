## Q: What is Contract? How Contract is Signed Between UI and Backend? Explain with Example?

**Answer:**

**What is Contract?**
- A **contract** is an agreement between frontend (UI) and backend services about the structure and format of data being exchanged
- It defines **what data will be returned**, **in what format**, **with which fields**, and **what types** those fields should be
- Contract ensures both UI and backend are on the same page about API responses

**How Contract is Signed?**
- Backend team designs the API and defines the **response structure** (JSON schema)
- Backend documents the API contract - what fields will be present, their types, and which are mandatory
- Frontend team receives this contract/documentation
- Frontend developers build UI components based on this contract
- Both teams agree on this structure before development starts

**Example:**

**Backend API Contract for User Endpoint:**

```json
{
  "endpoint": "/v1/users/{userId}",
  "method": "GET",
  "response": {
    "userId": "string (UUID)",
    "name": "string",
    "email": "string",
    "phoneNumber": "string",
    "age": "number",
    "isActive": "boolean",
    "createdAt": "string (ISO date format)"
  },
  "mandatory_fields": ["userId", "name", "email"],
  "example": {
    "userId": "user-65dde39e",
    "name": "John Doe",
    "email": "john@example.com",
    "phoneNumber": "9876543210",
    "age": 30,
    "isActive": true,
    "createdAt": "2024-01-15T10:30:00Z"
  }
}
```

**Backend Development:**
- Backend develops API as per contract above
- Returns response exactly as defined

**Frontend Development:**
- Frontend team reads contract
- Builds UI expecting these fields with these types
- Example:
  ```javascript
  // Frontend code
  const user = response.body;
  document.getElementById('name').textContent = user.name;  // Expects string
  document.getElementById('phone').textContent = user.phoneNumber;  // Expects string
  document.getElementById('age').textContent = user.age;  // Expects number
  ```

**Contract Break Scenario:**

Backend decides to change response without informing frontend:
- `phoneNumber` changed from **string** to **number**
  - Old contract: `"phoneNumber": "9876543210"` (string)
  - New contract: `"phoneNumber": 9876543210` (number)

**Impact on Frontend:**
- Frontend expects string but gets number
- UI might display incorrectly or crash
- Example: `"Phone: " + phoneNumber` might show `"Phone: 9876543210"` or `"Phone: [object Number]"` depending on JS handling

**Contract Testing Prevents This:**
- Tests validate that response matches the **agreed contract**
- If backend breaks contract, tests fail immediately
- Frontend team gets notified before UI breaks in production

## Q: What is Contract Testing or Schema Validation or Testing and Why is it Important?

**Answer:**

**What is Schema Validation / Contract Testing?**
- **Schema validation** is the process of **verifying that API responses match the expected structure and data types**
- It validates the **contract** (agreement) between frontend and backend
- Ensures API response has:
  - All mandatory fields present
  - No extra unexpected fields
  - Each field has the correct **data type** (string, number, boolean, array, object, etc.)
  - Fields are not blank/null when they shouldn't be

**Why is Contract Testing Important?**

**1. Catches Contract Breaks Early:**
- If backend changes response structure, contract testing catches it immediately
- Prevents bugs from reaching frontend or production

**2. Multi-Service Dependencies:**
- In E2E scenarios, one service depends on another service's response
- Service A returns data → Service B consumes it
- If Service A changes its response, Service B breaks
- Contract testing ensures Service A's response stays consistent

**Example E2E Dependency:**
```
Service 1 (User Service) → Returns userId
                                ↓
Service 2 (Order Service) → Creates order for userId
                                ↓
Service 3 (Payment Service) → Processes payment for order
```

- If User Service changes userId format (string to number), Order Service breaks
- Contract testing catches this immediately

**3. Prevents UI Crashes:**
- Frontend expects data in specific format
- If backend returns wrong type, UI might crash or display incorrectly
- Contract testing prevents this before it reaches users

**4. Ensures Data Consistency:**
- All mandatory fields must be present
- No null/blank values where data is required
- Correct data types throughout the response

**5. Maintains API Contract Documentation:**
- Schema acts as living documentation
- Shows exactly what the API returns
- Easier onboarding for new developers

## Q: In Schema Validation, What Do We Validate? Do We Validate Field Values or Data Types?

**Answer:**

**In schema validation, we validate DATA TYPES, NOT VALUES.**

**What We Validate:**
- **Data Type** of each field (is it string, number, boolean, array, object, etc.)
- **Presence** of mandatory fields (are all required fields present)
- **Structure** of response (is it object, array, nested structure, etc.)

**What We DON'T Validate in Schema Validation:**
- **Actual values** (we don't validate if name is "John" or "Jane")
- **Business logic** (we don't validate if age is 18+ for adult users)
- **Content correctness** (we don't validate if email is valid format)

**Example - Schema vs Value Validation:**

```javascript
// Response from backend
{
  "name": "John",      // String type
  "age": 30,           // Number type
  "email": "john@example.com",  // String type
  "isActive": true     // Boolean type
}
```

**Schema Validation (Type Check):**
```javascript
// ✅ Valid schema - All types are correct
const schema = {
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "age": { "type": "number" },
    "email": { "type": "string" },
    "isActive": { "type": "boolean" }
  },
  "required": ["name", "age", "email"]
};
```

**What Schema Validation Checks:**
- ✅ Is `name` a string? Yes
- ✅ Is `age` a number? Yes
- ✅ Is `email` a string? Yes
- ✅ Is `isActive` a boolean? Yes
- ✅ Are all required fields present? Yes
- **Schema validation PASSES**

**Broken Schema (Type Mismatch):**

If backend returns:
```javascript
{
  "name": "John",
  "age": "30",         // ❌ Changed to STRING instead of NUMBER
  "email": "john@example.com",
  "isActive": true
}
```

**Schema validation will FAIL:**
- ✅ Is `name` a string? Yes
- ❌ Is `age` a number? NO - it's a string "30"
- ✅ Is `email` a string? Yes
- ✅ Is `isActive` a boolean? Yes
- **Schema validation FAILS** - Type mismatch detected

**Value Validation (Separate - Not Part of Schema):**
```javascript
// Value validation checks actual data
expect(response.body.name).toBe("John");  // Checks specific value
expect(response.body.age).toBeGreaterThan(18);  // Checks business logic
expect(response.body.email).toMatch(/@/);  // Checks email format
```

**Summary:**
- **Schema Validation** = Type checking + structure checking
- **Value Validation** = Content and business logic checking
- They are different and serve different purposes

## Q: What is AJV Library and What Does It Do?

**Answer:**

**What is AJV?**
- **AJV** = Another JSON Schema Validator
- It's a **Node.js library** for validating JSON data against JSON schemas
- Validates if JSON data matches expected structure and data types
- Install: `npm install ajv`

**What Does AJV Do?**
- Takes a **JSON schema** (definition of expected structure)
- Takes **JSON data** (actual response from API)
- Compares data against schema
- Returns **true** if data matches schema
- Returns **false** with error details if data doesn't match schema

**How AJV Works:**

```javascript
import Ajv from 'ajv';

// Step 1: Create AJV instance
const ajv = new Ajv();

// Step 2: Define schema (expected structure)
const schema = {
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "age": { "type": "number" },
    "email": { "type": "string" }
  },
  "required": ["name", "age", "email"]
};

// Step 3: Compile schema (create validator function)
const validate = ajv.compile(schema);

// Step 4: Validate data against schema
const data = {
  "name": "John",
  "age": 30,
  "email": "john@example.com"
};

const isValid = validate(data);

if (isValid) {
  console.log("✅ Data is valid");
} else {
  console.log("❌ Data is invalid");
  console.log(validate.errors);  // Shows what failed
}
```

## Q: What Does Response JSON Schema Represent and What Information Does It Have?

**Answer:**

**What Does JSON Schema Represent?**
- A **JSON schema** is a blueprint/template that defines the **expected structure of a JSON response**
- It specifies what fields should be present, their data types, and whether they are mandatory
- Acts as a contract between backend and frontend

**What Information Does JSON Schema Have?**

**1. Type of Response:**
```json
{
  "type": "object"     // Response is a JSON object
}
```
OR
```json
{
  "type": "array"      // Response is a JSON array
}
```

**2. Properties (Field Definitions):**
```json
{
  "type": "object",
  "properties": {
    "userId": { "type": "string" },
    "name": { "type": "string" },
    "age": { "type": "number" },
    "skills": { "type": "array" },
    "address": { "type": "object" }
  }
}
```

- Each field and its expected data type is defined

**3. Required Fields:**
```json
{
  "type": "object",
  "properties": {
    "userId": { "type": "string" },
    "name": { "type": "string" },
    "email": { "type": "string" },
    "phone": { "type": "string" }
  },
  "required": ["userId", "name", "email"]
}
```

- `required` array specifies which fields MUST be present
- `phone` is optional (not in required array)

**4. Nested Objects:**
```json
{
  "type": "object",
  "properties": {
    "userId": { "type": "string" },
    "address": {
      "type": "object",
      "properties": {
        "city": { "type": "string" },
        "country": { "type": "string" }
      },
      "required": ["city"]
    }
  }
}
```

**5. Arrays with Items:**
```json
{
  "type": "object",
  "properties": {
    "userId": { "type": "string" },
    "skills": {
      "type": "array",
      "items": { "type": "string" }  // Array of strings
    }
  }
}
```

**Complete Example - User Schema:**

```json
{
  "type": "object",
  "properties": {
    "userId": { "type": "string" },
    "name": { "type": "string" },
    "email": { "type": "string" },
    "age": { "type": "number" },
    "isActive": { "type": "boolean" },
    "phone": { "type": "string" },
    "address": {
      "type": "object",
      "properties": {
        "city": { "type": "string" },
        "country": { "type": "string" }
      }
    },
    "skills": {
      "type": "array",
      "items": { "type": "string" }
    }
  },
  "required": ["userId", "name", "email", "age"]
}
```

**What This Schema Says:**
- Response is a JSON object
- Must have fields: `userId`, `name`, `email`, `age` (all required)
- Optional fields: `isActive`, `phone`, `address`, `skills`
- `userId`, `name`, `email`, `phone` are strings
- `age` is a number
- `isActive` is a boolean
- `address` is a nested object with `city` and `country` (both strings)
- `skills` is an array of strings

## Q: How to Read Schema from JSON File Instead of Hardcoding in Test?

**Answer:**

**Why Read from File?**
- Cleaner test files (no huge schema objects in code)
- Schemas can be reused across multiple tests
- Easier to update schemas in one place
- Schemas folder organizes all contracts in one location

**Setup:**

**Step 1: Create Schema File**

Create file: `src/schemas/userSchema.json`

```json
{
  "type": "object",
  "properties": {
    "userId": { "type": "string" },
    "name": { "type": "string" },
    "email": { "type": "string" },
    "age": { "type": "number" },
    "isActive": { "type": "boolean" },
    "createdAt": { "type": "string" }
  },
  "required": ["userId", "name", "email", "age"]
}
```

**Step 2: Import Schema in Test File**

```javascript
import Ajv from 'ajv';
import userSchema from '../../src/schemas/userSchema.json' with { type: 'json' };

// ✅ Import statement explanation:
// - Import schema directly from JSON file
// - `with { type: 'json' }`: Node.js automatically parses JSON into JS object
// - No need for fs.readFileSync or JSON.parse
// - userSchema is now a plain JavaScript object
```

**Step 3: Setup AJV and Validate**

```javascript
test('Get User - Schema Validation', async ({ apiHelper }) => {
    // Make API call
    const response = await apiHelper.get("/v1/users/user-65dde39e", AUTH_HEADER);

    expect(response.status).toBe(200);

    // Setup AJV
    const ajv = new Ajv();
    
    // Compile schema (create validator)
    const validate = ajv.compile(userSchema);
    
    // Validate response body against schema
    const isSchemaValid = validate(response.body);

    // Check if validation passed
    if (!isSchemaValid) {
        throw new Error(`Schema validation failed:\n${JSON.stringify(validate.errors, null, 2)}`);
    }

    // If we reach here, schema validation passed ✅
});
```

**Alternative Method Using fs.readFileSync (Older Approach):**

```javascript
import Ajv from 'ajv';
import fs from 'fs';
import path from 'path';

test('Get User - Schema Validation', async ({ apiHelper }) => {
    const response = await apiHelper.get("/v1/users/user-65dde39e", AUTH_HEADER);

    expect(response.status).toBe(200);

    // Read schema from file using fs
    const schemaPath = path.resolve(process.cwd(), 'src/schemas/userSchema.json');
    const userSchema = JSON.parse(fs.readFileSync(schemaPath, 'utf-8'));
    
    // Validation rest is same
    const ajv = new Ajv();
    const validate = ajv.compile(userSchema);
    const isSchemaValid = validate(response.body);

    if (!isSchemaValid) {
        throw new Error(`Schema validation failed:\n${JSON.stringify(validate.errors, null, 2)}`);
    }
});
```

**Why First Method is Better:**
- Simpler syntax (no fs or path required)
- Node.js automatically parses JSON
- `userSchema` is directly a JS object
- Better performance (no file reading at runtime)

## Q: Can We Create a Schema Validation Utility Instead of Repeating AJV Setup in Every Test?

**Answer:**

**Yes, absolutely! This is a best practice.**

**Problem with Current Approach:**
- Every test repeats AJV setup code
- Code duplication
- Difficult to modify validation logic in multiple places

**Solution: Create SchemaValidator Utility**

**Step 1: Create Utility File**

Create file: `src/utils/schemaValidator.ts`

```typescript
import Ajv, { JSONSchemaType } from 'ajv';

export class SchemaValidator {
    private ajv: Ajv;

    constructor() {
        this.ajv = new Ajv();
    }

    // Generic validation method
    validate(schema: any, data: any): { isValid: boolean; errors: any } {
        const validate = this.ajv.compile(schema);
        const isValid = validate(data);

        return {
            isValid: isValid,
            errors: validate.errors
        };
    }

    // Method with automatic error throwing
    validateAndThrow(schema: any, data: any): void {
        const result = this.validate(schema, data);
        
        if (!result.isValid) {
            throw new Error(
                `Schema validation failed:\n${JSON.stringify(result.errors, null, 2)}`
            );
        }
    }

    // Pretty print errors
    getErrorMessage(schema: any, data: any): string {
        const result = this.validate(schema, data);
        
        if (result.isValid) {
            return "Schema validation passed ✅";
        }
        
        return `Schema validation failed:\n${JSON.stringify(result.errors, null, 2)}`;
    }
}
```

**Step 2: Create Fixture for SchemaValidator**

Create file: `src/fixtures/schemaFixture.ts`

```typescript
import { test as base } from '@playwright/test';
import { SchemaValidator } from '../utils/schemaValidator';

type SchemaFixtures = {
    schemaValidator: SchemaValidator;
};

export const test = base.extend<SchemaFixtures>({
    schemaValidator: async ({}, use) => {
        const validator = new SchemaValidator();
        await use(validator);
    },
});

export { expect } from '@playwright/test';
```

**Step 3: Use in Tests**

```javascript
import { test, expect } from '../../src/fixtures/schemaFixture';
import userSchema from '../../src/schemas/userSchema.json' with { type: 'json' };

const AUTH_HEADER: Record<string, string> = {
    'X-API-Key': process.env.X_API_Key ?? '',
};

test('Get User - Schema Validation', async ({ apiHelper, schemaValidator }) => {
    // Make API call
    const response = await apiHelper.get("/v1/users/user-65dde39e", AUTH_HEADER);

    expect(response.status).toBe(200);

    // Validate schema - Simple one-liner
    schemaValidator.validateAndThrow(userSchema, response.body);

    // Test passed ✅
});
```

**Step 4: Combine with APIHelper Fixture**

Create file: `src/fixtures/apifixtures.ts` (Updated)

```typescript
import { test as base, expect } from '@playwright/test';
import { APIHelper } from '../utils/apiHelper';
import { SchemaValidator } from '../utils/schemaValidator';

type APIFixtures = {
    apiHelper: APIHelper;
    schemaValidator: SchemaValidator;
};

export const test = base.extend<APIFixtures>({
    apiHelper: async ({ request }, use) => {
        const apiHelper = new APIHelper(request, process.env.API_BASE_URL!);
        await use(apiHelper);
    },

    schemaValidator: async ({}, use) => {
        const validator = new SchemaValidator();
        await use(validator);
    },
});

export { expect };
```

**Step 5: Final Test Usage**

```javascript
import { test, expect } from '../../src/fixtures/apifixtures';
import userSchema from '../../src/schemas/userSchema.json' with { type: 'json' };

const AUTH_HEADER: Record<string, string> = {
    'X-API-Key': process.env.X_API_Key ?? '',
};

test('Get User - Schema Validation', async ({ apiHelper, schemaValidator }) => {
    const response = await apiHelper.get("/v1/users/user-65dde39e", AUTH_HEADER);

    expect(response.status).toBe(200);

    // One-liner schema validation
    schemaValidator.validateAndThrow(userSchema, response.body);
});

test('Create User - Schema Validation', async ({ apiHelper, schemaValidator }) => {
    const userData = {
        name: "Amit",
        email: "amit@example.com",
        age: 30
    };

    const response = await apiHelper.post("/v1/users", userData, AUTH_HEADER);

    expect(response.status).toBe(201);

    // Same validation method - reusable
    schemaValidator.validateAndThrow(userSchema, response.body);
});
```

**Benefits of This Approach:**

1. **Code Reusability:** Same utility used across all tests
2. **Single Source of Truth:** Validation logic in one place
3. **Easy Maintenance:** Update validation logic once, applies everywhere
4. **Clean Tests:** No AJV setup code in test files
5. **Multiple Validation Methods:** Can use `validate()`, `validateAndThrow()`, or `getErrorMessage()` based on need
6. **Fixture Integration:** Works seamlessly with other fixtures like `apiHelper`
